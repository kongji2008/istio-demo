# 03: Research: ambient AuthorizationPolicy / RequestAuthentication semantics in Istio 1.31

Type: research
Status: resolved
Blocked by:

## Question

The spec's policy layout rests on assumptions about how Istio ambient evaluates policy at ztunnel vs. waypoint. Verify each against primary sources (istio.io ambient docs: "Authorization policy" / "Use waypoint proxies" / "Configure waypoint proxies", the `AuthorizationPolicy` and `RequestAuthentication` reference pages, ztunnel docs, and Istio 1.31 release notes/upgrade notes for behaviour changes since 1.24):

1. **Namespace-wide empty-spec deny-all** (`spec: {}` with no `selector`/`targetRefs`): which enforcement points apply it: ztunnel on every captured workload in the namespace? the waypoint too? Cite.
2. **Waypoint → workload hop**: when a Service is enrolled to a waypoint, does ztunnel at the destination workload see the source principal as the *waypoint's* SA? If so, does the namespace deny-all block the waypoint→workload hop, requiring an L4 `ALLOW` for `cluster.local/ns/<ns>/sa/waypoint` in **both** `svc-a-ns` and `svc-b-ns`? Or does ztunnel treat traffic arriving from the workload's own waypoint specially? Cite exactly.
3. **L7 policy binding**: `AuthorizationPolicy` with `targetRefs` → `kind: Service` (enrolled to waypoint) vs. `targetRefs` → `kind: Gateway` (the waypoint). Which is correct/preferred in 1.31 for method/path rules and `requestPrincipals`? Confirm that an L7 field in a `selector`-bound policy evaluated by ztunnel is fail-safe DENY (cite the doc sentence).
4. **RequestAuthentication binding**: can it use `targetRefs` to a Service, or must it target the waypoint `Gateway`? Confirm the inline `jwks` field is supported and the `kid`/`alg` requirements. Confirm what happens to a request with *no* token when `RequestAuthentication` exists but no `requestPrincipals` rule matches (401 vs 403, and the response body).
5. **requestPrincipals format**: `<iss>/<sub>` and the `*` wildcard; the response the waypoint returns on denial (`RBAC: access denied`, status 403) so verify.sh can assert on it. What does ztunnel return for an L4 denial (connection reset vs. HTTP)? Scenario 2 in the spec expects the string `RBAC: access denied` from a `default`-ns curl pod hitting `service-a` (which has a waypoint): confirm which hop denies and what the client observes.
6. **PeerAuthentication STRICT in ambient**: how it is enforced by ztunnel and whether a namespace-scoped `PeerAuthentication` is sufficient (vs. mesh-wide in `istio-system`).
7. **Ingress Gateway → portal**: the Gateway API gateway's Envoy connects to ambient workloads over HBONE; confirm its identity as seen by `portal-ns` ztunnel is the gateway's own SA. Confirm whether a namespace-wide deny-all in the gateway's own namespace would indeed be enforced by the gateway's Envoy (the assumption behind ADR-0002); if not, note that too.
8. **Ad-hoc test pods**: is a `kubectl run` pod in an ambient-labelled namespace captured by ztunnel immediately (relevant to verify.sh scenarios 2–6)? Any caveat (e.g. pod must be created after the namespace label).

Write findings to `research/ambient-authz-semantics.md`, each claim cited with a URL. Close with a short "implications for the spec's k8s/3x-*.yaml layout" section: list any policy the spec is missing or has wrong. Then append the summary under `## Answer` in this file and set `Status: resolved`. Do **not** edit `map.md`.

## Answer

Full write-up with per-claim sources: `research/ambient-authz-semantics.md`.

1. **Empty-spec deny-all**: enforced by ztunnel on every captured pod in the namespace. Never applied by the Waypoint (policies without `targetRefs` are ignored by waypoints - `policyattachment.go`: "waypoints never use selector"), and the waypoint pod itself is not captured (`istio.io/dataplane-mode: none`). Opt-in flags `ENABLE_LAYERED_WAYPOINT_AUTHORIZATION_POLICIES` / `PILOT_AUTO_ALLOW_WAYPOINT_POLICY` exist but default off.
2. **Waypoint -> workload hop**: destination ztunnel sees the *Waypoint's* SA (`cluster.local/ns/<ns>/sa/waypoint`; SA = Gateway name), not the caller's. No special-casing. The namespace deny-all therefore blocks the hop; both `svc-a-ns` and `svc-b-ns` need an L4 ALLOW for their own waypoint SA. `principals: portal-sa` / `svc-a-sa` can only be checked at the Waypoint.
3. **L7 binding**: `targetRefs` kind `Service` (recommended for per-service rules) or kind `Gateway` (whole namespace) both work in 1.31. Doc sentence confirmed: a policy with L7 attributes "targeted such that it will be enforced by a receiving ztunnel ... will fail safe by becoming a `DENY` policy." `requestPrincipals` is L7.
4. **RequestAuthentication**: `targetRefs` kind `Service` supported ("waypoints only"); inline `jwks` supported; JWK needs `kty/n/e`, `kid` must match the JWT header if both present, `alg` optional (must be RS256 if set). No token -> passes authn unauthenticated -> `requestPrincipals` ALLOW fails -> **403 `RBAC: access denied`** (not 401). Invalid token -> 401 with body from jwt_verify_lib; wrong audience is the one 403 case. **Spec gap: `forwardOriginalToken: true` is required** or the in-app resource server never sees the token.
5. **requestPrincipals**: `<iss>/<sub>` -> `https://portal.internal/alice`; `https://portal.internal/*` for any Portal user. Waypoint denial = 403 `RBAC: access denied`. ztunnel denial = TCP close, no HTTP (curl exit 56). Scenario 2 only yields `RBAC: access denied` if the client namespace is ambient-enrolled (then the request traverses the Waypoint); a non-mesh `default` pod is dropped at L4 by ztunnel with no body.
6. **PeerAuthentication STRICT**: enforced by ztunnel (istiod converts it to a synthetic DENY of unauthenticated sources); namespace-scoped policy is sufficient; `DISABLE` is ignored; default PERMISSIVE.
7. **Ingress Gateway**: reaches portal over HBONE with its own SA `cluster.local/ns/istio-ingress/sa/<Gateway name>-istio`; gateway pod is not ztunnel-captured. ADR-0002 confirmed: a selector-less policy in the gateway's namespace is applied by the gateway's Envoy (`ENABLE_SELECTOR_BASED_K8S_GATEWAY_POLICY` default true). Ingress bypasses destination waypoints unless `istio.io/ingress-use-waypoint=true` (irrelevant here: portal-ns has no waypoint).
8. **Ad-hoc pods**: captured at sandbox creation (CNI plugin blocks start until ztunnel has the netns); pre-existing pods are enrolled in place. Caveats: `kubectl run` uses SA `default` (scenario 3 needs `--overrides` for `svc-a-sa`); scenario 2's client namespace must be ambient-labelled; verify with annotation `ambient.istio.io/redirection: enabled`.

**Spec corrections**: add `allow-waypoint-to-a` / `allow-waypoint-to-b` (L4, waypoint SA, both namespaces - item 8's condition is wrong); make `allow-portal-to-a` `targetRefs: Service` too; add `requestPrincipals` to both L7 policies; RequestAuthentication `targetRefs: Service` + `forwardOriginalToken: true`; optional per-namespace waypoint allow-nothing via `targetRefs: Gateway waypoint`; `allow-gw-to-portal` principal `<gw>-istio`; ambient-labelled test namespace for scenario 2; verify.sh expectations: S2 403 `RBAC: access denied`, S3 403 `RBAC: access denied`, S4 403 `RBAC: access denied`, S5 401 `Jwt is expired`, S6 401 `Jwt verification fails` (or `Jwks doesn't have key to match kid or alg from Jwt` if `kid` differs).
